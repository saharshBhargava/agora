# Setup: getting Agora running for the demo

Use **Tiger Cloud for Postgres** and **Render for the API + worker**. The iOS app is built in Xcode; it does
not need web hosting. Budget about 20 minutes after account creation, mostly waiting for deploys. Choose the
free plans explicitly and check the provider's displayed terms before creating resources. Step 6 needs the
URL from step 2. Public frontend configuration and a message to copy to teammates are in
[docs/frontend-handoff.md](docs/frontend-handoff.md).

| # | Account | Needed for | Required? |
|---|---|---|---|
| 1 | [Tiger Cloud](https://console.cloud.timescale.com) | Database (Postgres + TimescaleDB) | Yes |
| 2 | [Render](https://render.com) | Hosting the API | Yes |
| 3 | The team's existing Google Cloud project (Saharsh's) | Google sign-in + Calendar on the phone | Already set up; just add test users |
| 4 | [Google AI Studio](https://aistudio.google.com/apikey) | Gemini key for real fridge/pantry recognition | Recommended |
| 5 | Perceptron (ask at their sponsor table) | Perceptron vision instead of Gemini | Optional |
| 6 | A new Gmail account for the demo (step 3b) | Signing in to the pre-filled demo account from the iOS app | Yes, for demos |

**What to send back to Kedar's coding session when you're done:** just the Render URL (it's public, not a secret).
With it, the deploy can be smoke-tested end to end and the keep-warm job pointed at it. Never send the Tiger
connection string or any API key; those only ever go into Render.

Never paste keys into the repo, chat or Slack. They go only into Render's environment settings (and the iOS
app's own Settings screen for the on-device Gemini key).

## What each URL and credential means

| Value | Where to get it | Where to put it | Share with frontend? |
|---|---|---|---|
| Database connection string | Tiger service > Connect; direct Postgres URL, including password and SSL parameters | Render `AGORA_DATABASE_URL` | No |
| Public API origin | Render service overview after deployment, `https://<actual-host>.onrender.com` | iOS `AGORA_API_BASE_URL`; GitHub Actions variable `AGORA_API_URL` | Yes |
| Versioned API root | Public origin + `/v1` | For API reference; iOS config still takes just the origin | Yes |
| Interactive docs / schema | Origin + `/docs` and `/openapi.json` | Open in browser; schema for client generation | Yes |
| Google iOS client ID and reversed ID | Already in `Config/Agora.xcconfig` | Inherit in iOS; matching client ID is preset in Render | Yes, public IDs |
| Backend Gemini key | Google AI Studio > API keys | Render `AGORA_GEMINI_API_KEY` | No |
| On-device Gemini key | A separate key/project in AI Studio | Each tester's app Settings; private transfer if needed | Only privately to testers; never source code |
| Demo Google account | Create a Google account; add it as an OAuth test user | Render `AGORA_DEMO_GOOGLE_EMAILS` | Address yes; password privately |
| Demo API password | Generated by Blueprint; Render service > Environment > `AGORA_DEMO_PASSWORD` | Private API testing only | Privately if needed |
| Dev JWT signing secret | Generated by Blueprint in Render | Render `AGORA_DEV_JWT_SECRET`; preserve across deploys | No |
| Per-user API bearer token | Google Sign-In SDK supplies a fresh **ID token** | `Authorization: Bearer <token>` on API requests | Generated per session; no static shared API key |

Real secret values stay outside Git. The repo contains variable names, public client IDs and examples.
GitHub Actions does not need database credentials or provider API keys for the existing CI/deployment flow.
No Render API token, S3 bucket, Google web-client secret or custom domain is needed for this setup.

## 1. Database: Tiger Cloud (about 3 min)

1. Sign up at [Tiger Console](https://console.cloud.timescale.com). Choose **New service** and the
   **Free / Shared** option, with TimescaleDB enabled. Avoid selecting the separate paid-service trial by
   accident. Free regions can be restricted; use the offered free region (currently US East).
2. Open the service, then **Connect**, and copy the connection string. It looks like
   `postgres://tsdbadmin:<password>@<host>:<port>/tsdb?sslmode=require`. Use the direct URL, not a pooler URL.
3. Save the database password and full URL in your password manager. Copy the provider's URL without changing
   its host, port, database name or SSL parameters. Use the service's admin/owner credentials: migrations
   create the `agora_rw` role and grant it to the connection user.

The schema and demo data are created automatically on first boot; there's nothing to run by hand.

## 2. API: Render (about 10 min, mostly build time)

Shortcut: open [Deploy Agora on Render](https://render.com/deploy?repo=https://github.com/saharshBhargava/agora)
to start the Blueprint flow directly. The generic service-type picker is not needed.

1. Sign in to Render with GitHub. **New > Blueprint**, then choose `saharshBhargava/agora`. Render reads
   `render.yaml` from **main** in the repo. If Render can't see the repo, the repo owner (Saharsh) has to grant Render's
   GitHub app access to it.
2. Render asks for the variables marked as secrets:
   - `AGORA_DATABASE_URL`: the Tiger connection string from step 1.
   - `AGORA_DEMO_GOOGLE_EMAILS`: the Google address you will use for the populated demo account (step 3b).
     If you have not created it yet, leave this blank; ordinary approved Google accounts can still sign in.
   - `AGORA_GEMINI_API_KEY`: from step 4 if you have it already; otherwise leave it blank for now.
   - Leave `AGORA_PERCEPTRON_API_KEY` blank unless you have one.
3. Confirm the API service uses the **Free** plan, then **Apply**. Do not create a separate Render database
   or worker. The container runs migrations and the worker itself; photos are stored in Tiger.
4. When Render says **Live**, copy its exact public service URL from the overview. The name may have a suffix;
   do not guess it from `agora-api`. Open `<origin>/readyz` and expect HTTP 200 with
   `{"ok": true, "timescale": true, ...}`. Save the **origin only**, without `/readyz`, `/v1` or a trailing slash.
   This is what the frontend needs. Render supplies HTTPS; no domain purchase is required.

Everything else is preset in `render.yaml`:
- demo mode, with a generated dev-token secret
- Google sign-in, using the iOS client ID from `Config/Agora.xcconfig`
- database-backed photo storage
- the demo account created and filled on boot (step 3b)
- a generated `AGORA_DEMO_PASSWORD` (find it under the service's **Environment** tab)
- `main` as the deployment branch, with automatic deploys waiting for passing CI checks
- `AGORA_SEED_NEW_USERS=false`, keeping ordinary accounts free of sample data

If an optional blank value prevents Blueprint creation, remove that optional variable from the creation
form and add it later under the service's **Environment** tab. Do not use made-up keys. Missing vision keys
allow startup but only recorded replay photos can be processed. For an existing Blueprint, add new secret
variables directly in **Environment**: `sync: false` only prompts during initial creation.

## 3. Google sign-in + Calendar (about 2 min)

The phone signs in with Google and talks to Google Calendar directly. The backend only checks the Google ID
token the phone sends for inventory calls. The Google Cloud project and iOS OAuth client already exist; their
public IDs are in `Config/Agora.xcconfig`, and `render.yaml` uses the same client ID. While the OAuth app is in
**Testing**, only listed accounts can sign in, so:

- **Saharsh** (project owner): Google Cloud console, then **Google Auth Platform > Audience > Test users**. Add
  the Google account of every teammate and of the demo phone.

That's all. There's no web client, client secret or redirect URL to configure. If you ever switch to your own
Google Cloud project, follow "One-time Google Cloud setup" in `backend/README.md`, then set
`AGORA_GOOGLE_IOS_CLIENT_ID` in Render to the new client ID, since it must match the app's. In Testing mode,
Google expires Calendar consent after 7 days, so you may need to sign in again during a long weekend.

## 3b. The demo account (about 5 min)

The backend has one designated **demo account**, pre-filled with about a month of realistic history:
- fridge/pantry scans with detections, plus consumption history
- stores and purchase dates
- preferred stores
- wishlist items and agent suggestions (pending, accepted, snoozed, rejected), with thumbs feedback

From the UI it looks exactly like a real, well-used account; nothing in the app says it's a demo. Anything
simulated (payments, once they exist) is switched on only for this account, and real accounts never get fake
data or fake behaviour. One account, two ways in:

1. **From the iOS app (for demos):**
   - Create a fresh Gmail account that looks like a real person's, e.g. `alex.rivera.agora@gmail.com`. You need
     to make it yourself.
   - Ask Saharsh to add it under **Test users** (step 3).
   - In Render, set `AGORA_DEMO_GOOGLE_EMAILS` to that address and save. Render redeploys.

   Signing in with that Google account on the phone now opens the demo account. Its credentials are that
   Gmail address and the password you chose for it.
2. **From curl, the API docs page or a desktop build:** `POST /v1/dev/login` with
   `{"handle": "demo", "password": "<AGORA_DEMO_PASSWORD>"}`. The password is in Render, under the service's
   **Environment** tab, generated for you. Treat it like any password.

Inside the app, the account is "Alex Rivera" (handle `alexrivera`). To start fresh after rehearsals (this wipes
only the demo account and recreates it), run from `backend/`:

```bash
uv run python -m app.tools.demo reset --database-url "<tiger url>"
```

Teammates' own Google accounts stay ordinary, empty accounts: use them to show "a new user" if you want.

## 4. Gemini key (about 2 min)

1. Open [Google AI Studio > API keys](https://aistudio.google.com/apikey), select or create a Google Cloud
   project, then **Create API key**. Copy the key privately. Check the project's available quota/billing.
2. Render, then **Environment**: set `AGORA_GEMINI_API_KEY` and save. Backend scans now use Gemini vision. Without a key
   they only work for pre-recorded replay fixtures, and the server logs a warning instead of crashing.
3. The iOS chat agent uses a key entered in the app's **Settings** tab. Use a separate tester key/project so
   on-device usage does not consume the backend's quota or require sharing the backend credential. Do not
   embed a provider key in a distributed app binary; this Settings flow is for trusted demo testers.

## 5. Perceptron (optional)

If the Perceptron sponsor gives you a key, set these in Render: `AGORA_PERCEPTRON_API_KEY=<key>`,
`AGORA_VISION_PROVIDER=perceptron`, `AGORA_VISION_FALLBACK=gemini`. If Perceptron errors or times out,
Gemini takes over for that frame automatically.

## 6. Point the iOS app at it

Copy `Config/Local.xcconfig.example` to `Config/Local.xcconfig` (gitignored) and set:

```xcconfig
AGORA_API_BASE_URL = https:/$()/<your-service>.onrender.com
```

The `$()` is intentional: it stops xcconfig from treating `//` as a comment. The example leaves Google
overrides commented so the team's working IDs are inherited; only override both if using your own project.
Rebuild. Calendar and chat work without this; the Home screen's
inventory needs it.

Send teammates the filled-in [frontend handoff](docs/frontend-handoff.md). They need the API origin and
Google test-user access, not the database URL or a backend API key. Browser-based clients additionally need
their exact origin added to Render's `AGORA_CORS_ORIGINS` as a JSON array, for example
`["https://frontend.example.com","http://localhost:3000"]`. Native iOS does not use CORS. A browser Google
client ID is not automatically accepted by this iOS-configured backend; agree on that auth flow before
connecting a web frontend.

## 7. Check it works

First check readiness (on Windows use `curl.exe`; replace the host):

```bash
curl -s https://<your-service>.onrender.com/readyz
```

Then test authentication and data. In PowerShell, this prompts for the password instead of saving it in
shell history, and does not print the token:

```powershell
$api = "https://<your-service>.onrender.com"
$demoCredential = Get-Credential -UserName demo -Message "Use AGORA_DEMO_PASSWORD from Render"
$loginBody = @{ handle = "demo"; password = $demoCredential.GetNetworkCredential().Password } | ConvertTo-Json
$session = Invoke-RestMethod "$api/v1/dev/login" -Method Post -ContentType "application/json" -Body $loginBody
$headers = @{ Authorization = "Bearer $($session.access_token)" }
Invoke-RestMethod "$api/v1/me" -Headers $headers
Invoke-RestMethod "$api/v1/inventory" -Headers $headers
Remove-Variable loginBody, session, headers, demoCredential
```

Open `<origin>/docs` to inspect request/response schemas. Protected endpoints currently read the
Authorization header directly and do not expose a Swagger Authorize control; use the PowerShell example
above for authenticated testing. `/v1/me` should identify Alex Rivera and `/v1/inventory` should contain
seeded items. An unauthenticated request to `/v1/me` should return 401.
Finally sign in on the phone with the demo Gmail and approve Calendar. Verify inventory, a real photo scan
(requires the vision key), and a Calendar event. Calendar traffic goes directly from the phone to Google.

## 8. Keep it alive until the demo

| Risk over the next ~15 hours | Likelihood | What protects you |
|---|---|---|
| Render free server **sleeps** after 15 idle min (first request then takes ~1 min) | Certain, unless pinged | `keep-warm` workflow (below) + an uptime monitor + opening `/healthz` 5 min before presenting |
| Render **restarts** the free server at any time | Occasional | Harmless: all state is in the database, and in-flight scans resume from the job queue |
| Render **monthly hours** (750) or bandwidth run out | Very unlikely in a day | Plan B below |
| A last-minute merge to `main` **auto-deploys a bad build** | Real: other sessions are merging PRs | Freeze deploys (below) |
| Tiger free service **storage** limit is reached | Depends on testing volume | Tiger can become read-only; `/readyz` only checks connectivity, so also test a write; snapshot + Plan B |
| Tiger free service **pauses or misbehaves** (free plan is beta; idle behaviour isn't documented) | Unlikely | Keep-warm pings also hit the database; snapshot + Plan B |
| **Gemini quota** runs out (check current limits in AI Studio; each scan frame can invoke the provider) | Depends on testing volume | Separate projects per use (below); replay fixtures; the cache avoids repeated provider calls for processed photos |
| Google test-user consent expires (7 days in Testing) | Not within a day | Sign in again |

**Do these now:**

1. **Keep it awake.** Two layers:
   - Ask Saharsh (repo admin) to add the repository variable `AGORA_API_URL` = your Render URL, under
     **Settings > Secrets and variables > Actions > Variables**. `.github/workflows/keep-warm.yml` then pings it
     every 10 minutes. GitHub can delay scheduled runs, so also:
   - Create a free uptime monitor (e.g. UptimeRobot, no card) on `https://<your-service>.onrender.com/healthz`
     every 5 minutes.
2. **Spread the Gemini quota.** Quotas are per Google Cloud project, so create keys in **different projects**:
   - one for the backend (`AGORA_GEMINI_API_KEY` in Render)
   - one for the iOS chat agent (app Settings)
   - one spare that nobody uses until demo time

   Test scans with 1–3 photos, not 12. If a key hits its limit, paste the spare into Render; it redeploys in
   about a minute. Only change `AGORA_GEMINI_MODEL` after checking the model is available to that project and
   supports the vision requests used here; model availability and limits change.
3. **Record the demo scans once** with a real key, then make them replayable offline. From `backend/`:
   `AGORA_DATABASE_URL=<tiger url> uv run python -m app.tools.export_replay`, then commit `backend/seed/replay/`.
   Setting `AGORA_VISION_PROVIDER=replay` then gives identical results for those photos with no API calls.
4. **Freeze 2–3 hours before presenting.** Render service, then **Settings > Auto-Deploy: Off**. Note the commit
   on the **Events** tab, and tag it so you can always go back:

   ```bash
   git tag demo-ready <commit> && git push origin demo-ready
   ```

   Render only rolls back to the last two deploys, so the tag is your real undo button.
5. **Snapshot the data** after your final rehearsal (and again before presenting). It includes everything you
   created while testing:

   ```bash
   cd backend && uv run python -m app.tools.snapshot export ../demo-snapshot.zip --database-url "<tiger url>"
   ```

   Keep `demo-snapshot.zip` on two laptops. It's personal demo data, so don't commit it.
6. **Record backup videos** of each flow early, while everything works.

## 9. Plan B: run everything on a laptop

If hosting fails, a laptop runs the identical backend: same code, migrations, demo account, Google sign-in
and features. The iOS app talks to it as if it were the hosted server. Prepare one laptop (ideally the Mac you
demo from) **today**, so Plan B is a single command later.

One-time prep (macOS):

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
```

```bash
brew install cloudflared
```

Docker Desktop is optional. Without it the script uses an embedded Postgres it downloads itself; that one has no
TimescaleDB, and the app switches to its plain-SQL path automatically. Then clone the repo, and from
`backend/`, run it once to check it works:

```bash
uv run python -m app.tools.local_demo --tunnel
```

It starts the database, runs migrations, creates the demo account and starts the API on `http://localhost:8000`.
It prints the local demo password, which is kept in `backend/.data/` so it doesn't change between runs. To reach
the demo account from the iOS app locally, first run `export AGORA_DEMO_GOOGLE_EMAILS=<demo gmail>`.
`--tunnel` adds a public `https://….trycloudflare.com` URL (free, no account) and writes it into
`Config/Local.xcconfig`. Rebuild the iOS app in Xcode and it uses the laptop. A `backend/.env` with
`AGORA_GEMINI_API_KEY=...` enables real scans; without it, only replay fixtures work.

Which command to use, by what failed:

| What failed | Do this (from `backend/`) | Data you'll see |
|---|---|---|
| Render only (database still up) | `uv run python -m app.tools.local_demo --tunnel --database-url "<tiger url>"` | Everything, live |
| Render **and** Tiger | `uv run python -m app.tools.local_demo --tunnel --import-snapshot ../demo-snapshot.zip` | Everything up to your last snapshot |
| Venue wifi | Use a phone hotspot for the laptop and phone, then either command above | Same |
| No internet at all | Google sign-in, Calendar and Gemini chat can't work on any setup. Scans and inventory work locally with replay fixtures (`AGORA_VISION_PROVIDER=replay`). The iOS app currently only accepts HTTPS backends, so show this via `http://localhost:8000/docs` or the backup video | Seeded data + replayed scans |

Each `--tunnel` run gets a new URL. Rebuild the iOS app after starting it (the script updates the config for you).

## Troubleshooting

| Symptom | Fix |
|---|---|
| Deploy fails at boot | Check Render's **Logs**. A config error names the exact variable. A missing or wrong `AGORA_DATABASE_URL` is the usual cause |
| `/readyz` shows `"timescale": false` | The database isn't Tiger (or the extension is off). Everything still works, with plain-SQL fallbacks |
| Google says the app is blocked or access denied | Saharsh adds that Google account under **Audience > Test users** |
| Home says inventory isn't available | `AGORA_API_BASE_URL` isn't set in `Config/Local.xcconfig`, or isn't `https://` with no path |
| Inventory fails to load after signing in | `AGORA_GOOGLE_IOS_CLIENT_ID` on Render doesn't match the app's client ID, or the server is still waking up |
| Render build has no checks to wait for | Confirm the service deploys `main` and GitHub Actions is enabled; `render.yaml` changes run the backend workflow too |
| Migration says permission denied creating role or setting role | Use Tiger's service owner/admin direct connection, not a restricted application user; the initial migration creates and grants `agora_rw` |
| Database connection times out | Check Tiger service is running, copied host/port are correct, and any IP allowlist permits Render outbound addresses (shown in Render's service dashboard) |
| A scan fails with `no_replay_fixture` | No vision key is set and that photo wasn't pre-recorded. Add the Gemini key (step 4) |
| Scans fail with `provider_rate_limited` | Gemini quota hit: paste the spare key (section 8, step 2) or switch to `replay` |
| `local_demo` says port in use | Another server is on 8000: add `--port 8001` |

## If a free tier runs out

Nothing in the code is tied to these providers. Switching only means changing environment variables, for
example moving the database to Neon or Supabase, or hosting on Railway, Koyeb, Fly.io or a laptop with a
`cloudflared` tunnel. The full table is in [backend/README.md](backend/README.md#switching-when-something-runs-out).
